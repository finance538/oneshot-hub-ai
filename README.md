# 1SHOTCAM.COM — OneShot Ecosystem

An Arabic React/Vite ecosystem combining the original OneShot public storefront with the gateway workspace, encrypted administrator vault, advisory executive office and AI Workforce digital headquarters through Netlify AI Gateway. The storefront supports localized marketing and light/dark appearances.

## Technology and local development

- React 19, TypeScript and Vite for the responsive client.
- Netlify Functions for JSON APIs and server-side authorization.
- Netlify Database (managed PostgreSQL) through `@netlify/database` and Drizzle's Netlify adapter.
- Netlify Identity for account creation, invitations, recovery and administrator roles.
- Google GenAI SDK through Netlify AI Gateway for chat and executive requests; direct Stripe hosted checkout from Netlify Functions for new payments.
- Netlify Image CDN for the product concept images.

Install with `pnpm install`. Link the project with Netlify CLI, then run `netlify dev --port 8889` for local development with Functions and Identity. Plain `pnpm dev` serves the client only. `npm run build` is the deployment build command; Netlify publishes `dist`. Local build, test, dev-server and type-check commands were not run during this implementation; the deployment pipeline performs validation.

The template service was unavailable, so the application was assembled directly with React and Vite. No template demo content remains.

## Payment flow and compatibility

New payments use Stripe Checkout, with `HOSTED_PAGE` or `PAYMENT_LINK`. Both create an individual hosted Checkout Session, not a reusable Stripe Payment Link resource. Other gateways and topologies fail explicitly before creating an order or contacting a provider. The uploaded PayTabs/Telr/generic adapters are not considered verified production integrations and are not enabled by this migration. Saved credentials for those providers are retained; using Stripe requires an explicit selection and matching merchant credentials. No merchant is silently switched to another provider. `/api/payments/capabilities` describes the implemented adapter, not merchant account readiness.

`POST /api/gateways/execute-live` and its existing aliases require Identity and an `Idempotency-Key`; arbitrary workspace payments require an administrator. Imported service catalog entries still require a scoped quote and reject direct checkout with `SERVICE_QUOTE_REQUIRED`. The order is saved before contacting Stripe. One provider request is made, with the same idempotency key, using a fixed HTTPS endpoint and no redirects or retries. PAN/CVV and nested raw card objects are rejected. The hosted page collects the card and requests 3D Secure; bank/provider decisions remain authoritative. No VPN, fingerprint or AVS checks are presented as completed controls. All-mode diagnostics create zero charges.

The implementation pins Stripe API version `2026-09-30.endive`; request fields were inspected against Stripe's public OpenAPI specification. No live or test charge was made during implementation. Checkout redirects are restricted to Stripe's HTTPS checkout domain and open externally. Provider errors, HTML or transport loss leave an unconfirmed order. Repeating the same operation key returns that existing order without another provider call. An unknown result with no saved Stripe session ID requires reconciliation in the merchant dashboard; this code does not blindly retry the charge or infer a session ID.

`POST /api/orders/:id/reconcile` is authenticated, rate limited and restricted to the owner. It retrieves the session from Stripe and requires exact order/client-reference/metadata, amount, currency, environment, mode and session ID matching. Only a complete, paid session becomes `paid`; a verified expired unpaid session becomes `failed`. Browser navigation or an iframe event never confirms payment. Receipts and order updates are transactional and idempotent; a paid order is never downgraded. The UI polls reconciliation for new orders, and the production-only scheduled Function processes up to three pending sessions every five minutes, rotating unconfirmed entries. This is bounded background processing, not an instant webhook SLA; higher volume needs capacity review.

The normalized HMAC endpoint `/api/webhooks/callback` remains for **legacy_core orders only**. It rejects events targeting new Netlify orders, verifies the existing five-minute timestamp window and HMAC over `timestamp + '.' + raw_body`, matches amount/currency/gateway/environment and deduplicates transactionally. Its headers remain `x-oneshot-timestamp` and `x-oneshot-signature`; required JSON fields remain `eventId`, `orderId`, `gatewayCode`, `executionMode`, `amountCents`, `currency`, `status`. It does not accept native provider webhook formats. Keep the old core available for outstanding legacy confirmations until reconciled.

Health now checks Netlify application/database availability, not VPS or merchant connectivity. The readiness screen separates application configuration from a verified native live-payment receipt. No deployment, live inference, data import, domain transfer or VPS shutdown is asserted by source changes.

## Routing and cache behavior

Both `_redirects` copies and `netlify.toml` place `/api/*` before the SPA fallback. The forced rewrite targets the server Function so auth, encryption, idempotency and persistent order tracking cannot be bypassed by a generic HTTP proxy. Redirect targets are plain URLs, not Markdown links. `public/_redirects` is copied into the Vite publish directory.

`callBackendApi(endpoints, payload)` reads response text before parsing JSON. An HTML response produces a useful error; there is no VPS fallback, including for health. Financial, vault and AI requests never fall through to an unverified browser-origin API that bypasses local authorization and persistence. Safe alias fallback is supported by the server and local router.

The early head script unregisters old service workers and clears Cache Storage. `Clear-Site-Data` clears cache only; clearing storage on every response would invalidate Identity sessions. Runtime responses are `no-store`. The root HTML contains finished Arabic site name, description and sharing metadata, without an `og:image` override.

Hostname defaults are: root/www → store, portal/pay → gateway and admin → vault. The legacy `ai`/`app` root entry and `?module=ai` bookmarks are normalized to `/workforce` without reloading, preserving language, theme and Identity callback fragments. Active module links use `?module=store|gateway|vault|ceo`. API authorization remains server-side regardless of which hostname or tab is open. These application routes do not change hostname assignments or DNS.

Start a voice call for automatic listen/reply turns, or hold the microphone button or Space outside text controls. Escape ends audio. SpeechRecognition provides browser transcription when supported and switches to Gateway on network/language-service failure; the Gateway route records short clips with MediaRecorder and transcribes them with the official Gemini SDK. Gateway clips stop after detected silence or at 15 seconds, are size/rate limited and are not stored by the application. The browser speech service may process audio remotely. Final transcripts and responses are saved as conversation text. Neither route grants AI execution tools or external account permissions.

It performs successive recognition, model and synthesis turns. The waveform measures microphone samples, while the employee ring follows synthesis playback events rather than fabricated output amplitude. Mute preserves written replies.

The current headquarters view replaces the runtime Three.js scene with a layered SVG/HTML 2.5D office: charcoal architectural panels, warm ceiling lighting, illuminated oneShot lettering, filing cabinets, glass workstations and illustrated suited employees. It is a stylized architectural scene, not a photographic render or a claim of matching an unavailable reference image. The old engine source remains unused; headquarters no longer imports or initializes it. This section supersedes the earlier first-person-engine presentation and navigation descriptions.

A paged composition shows the CEO and up to four specialists at a time; the dock dropdown reaches every catalog employee without overlapping a full team's labels. Selecting a person pans/zooms toward the desk; selecting their monitor opens the corresponding workspace. Dragging adjusts the view, and reduced-motion preferences disable camera transitions. Only one activity ticker appears above the scene, with full text available on demand. Monitor snippets come from owned conversations, recorded activity or tasks; empty states remain explicit.

The office fills the workspace; chat opens on demand in a native side drawer on desktop and mobile. Meetings open in a separate dialog. Microphone controls and the real analyser waveform share the composer, and permission/provider failures stay in the chat rather than covering the office. Existing browser/Gateway transcription and local/Azure speech dependencies remain unchanged; this frontend change cannot guarantee audible speech without runtime setup and device permissions.

Mail and research monitors open the existing authenticated inbox, draft approval, research and vault tools. Other monitors open owned chat and an editable task-output draft; submitting a revision saves a new conversation request through the existing API and preserves the original task output. Local edits are not autosaved and are cleared when changing the selected task or closing the screen. Specialist roles remain advisory and cannot publish code or execute arbitrary external changes. The Master PC retains access to every employee's saved task screens and operations. No database or migration changes were made; earlier deployment blockers remain separate. Build, tests and device/browser validation were not run during this change.

## Visual restoration and compact navigation

The storefront and workforce now share the original imported storefront's charcoal background (`#0b0d0f`), panel (`#14181d`) and subtle 1px border palette, with the established IBM Plex Sans Arabic/Outfit typography. Shared tokens control compact 36px desktop buttons, 44px coarse-pointer targets, 12px control text, 14px body copy and restrained responsive headings. Orange is concentrated on primary actions; selected tabs, secondary buttons, card outlines and descriptive icons use neutral colors. Light mode and RTL remain supported.

The homepage has shorter Arabic/English introductory copy and concise headquarters entry labels in all eight marketing languages. Catalog preview cards retain price, status and detail/request links while leaving deliverable lists to the full catalog and detail pages. The workforce market starts with six employees and offers more on request; search and category changes reset the visible count. Employee cards show a short bio and two skills, with the full bio, skills and capability limitations in the existing trial dialog.

The main office keeps the scene or conversation in focus. Task history, activity, meeting minutes and task tools open from the Tasks control; full activity text and team contributions open in dialogs. Conversation settings collect employee selection, output language, speech route, voice selection, audio diagnostics, refresh and connected tools behind one header button. The composer keeps text entry, microphone, mute and send visible. Shared native dialogs provide focus containment, Escape dismissal, backdrop dismissal, scroll locking and focus restoration. Opening settings does not initiate microphone access or change configured services.
